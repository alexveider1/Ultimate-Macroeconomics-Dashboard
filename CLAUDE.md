# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`Ultimate Macroeconomics Dashboard` is a 9-container Docker stack: a Streamlit multi-page dashboard backed by Postgres + Qdrant, with FastAPI micro-services for the AI analyst, forecasting, clustering, on-demand data ingestion, and a sandboxed Python executor. Read `README.md` for the full description; the sections below cover only what isn't obvious from the code.

Planning docs: `TODO.md` is the flat, actionable backlog; the detailed phased roadmap (rationale, sequencing, per-phase touchpoints, locked "Guiding decisions") lives in `.claude/roadmap.md` (the former root-level `PLAN.md`).

## Running the stack

Linting/formatting is done with `ruff` and type-checking with `ty` (both Astral); each service ships a `[dependency-groups] dev` block with both plus `pytest` and `pytest-cov`. Ruff and ty are configured **once at the repo root** in `ruff.toml` and `ty.toml` (single source of truth) — the per-service `pyproject.toml` files intentionally carry no `[tool.ruff]`/`[tool.ty]` tables, so running `ruff`/`ty` from any service directory walks up and resolves the root config (each service's own `.venv` is still used for import resolution). The root `ruff.toml` turns on import sorting (isort `I` with `combine-as-imports` + `force-sort-within-sections`) plus formatter niceties (`lf` line endings, docstring code formatting). Tests live under `<service>/tests/` and run via `uv run pytest` — `[tool.pytest.ini_options].addopts` enables coverage by default (`--cov --cov-report=term-missing`), with per-service `[tool.coverage.run].source` pointing at that service's package(s). Everything runs inside containers via Docker Compose. Every service is Python 3.12 and uses [uv](https://docs.astral.sh/uv/) for dependency management — each service has its own `pyproject.toml` + `uv.lock`, and the Dockerfile runs `uv sync --frozen` into `/opt/venv`.

```bash
# Full stack (build + run, foreground)
docker compose up --build

# Single service rebuild
docker compose build agent
docker compose up -d agent

# Logs
docker compose logs -f app
docker compose logs -f agent
```

For local iteration without rebuilding the image, work in any service directory:

```bash
cd app           # or agent, forecaster, etc.
uv sync          # creates .venv from pyproject.toml + uv.lock
uv run python -m streamlit run app.py   # or uvicorn main:app for FastAPI services
uv add <package>      # add a dependency (updates pyproject.toml + uv.lock)
uv lock --upgrade     # refresh the lockfile
```

First boot requires `_container_data/.env` (copy from `_container_data/.env.example`) and a populated LLM section in `_container_data/config.yaml`. The `postgres:18` image creates the superuser (`POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB`) natively on first volume init; `downloader_general` then upserts the read-only LLM role via `src/utils/db_bootstrap.py` (also grants `SELECT` on `public` plus default privileges, so future tables are readable automatically) and runs the ingestion (~1–2h) for World Bank + Yahoo Finance + Webz.io news. The dashboard is at `http://localhost:8501`.

The bootstrap step runs on **every** `downloader_general` container start (cheap, idempotent), so rotating `POSTGRES_LLM_PASSWORD` or adding new tables in a future release takes effect on the next `docker compose up -d downloader_general` without wiping volumes. Only the **initial** bulk download is one-shot, gated by `_container_data/downloader_general/.download_completed`. After that marker is written the container **does not exit** — it stays up running a per-source incremental update scheduler (see the `scheduler:` block in `config.yaml` and the "Data ingestion" section). Because the container is now long-running, its Compose `depends_on` gate flipped from `service_completed_successfully` to `service_healthy` (the healthcheck just tests for the marker file), and `restart:` is `unless-stopped`.

If the host has no NVIDIA GPU, remove the `deploy:` block from the `forecaster` service in `docker-compose.yaml` (the `chronos` model will be skipped; every other model — `auto_arima`, manual `arima`, `sarima`, `prophet`, `moving_average`, `xgboost` — runs CPU-only).

## Architecture

### Service map and ports

| Service              | Port | Role                                                                                                                  |
| -------------------- | ---- | --------------------------------------------------------------------------------------------------------------------- |
| `db`                 | 5432 | Postgres 18 — World Bank + Yahoo Finance + Binance crypto + FRED US-state + Eurostat EU-NUTS2 tabular data            |
| `vector_db`          | 6333 | Qdrant — news + curated-news (Actually Relevant) + World Bank document embeddings                                     |
| `downloader_general` | —    | Initial one-shot ingest (bootstraps LLM role, ingests WB + Yahoo + Binance + FRED + Eurostat + news), **then long-running**: a per-source incremental update scheduler keeps both DBs fresh |
| `app`                | 8501 | Streamlit dashboard (entry point: `app/app.py`)                                                                       |
| `agent`              | 8000 | FastAPI — LangGraph multi-agent AI analyst                                                                            |
| `forecaster`         | 8001 | FastAPI — forecasting (ARIMA family, Prophet, Chronos, MA, XGBoost)                                                   |
| `clustering`         | 8002 | FastAPI — KMeans / DBSCAN                                                                                             |
| `downloader_extra`   | 8003 | FastAPI — on-demand WB indicator / Yahoo ticker / Binance pair / FRED state-indicator / Eurostat NUTS-2 dataset ingestion (called by the agent) |
| `python_sandbox`     | 8004 | FastAPI — isolated executor for LLM-generated Plotly/Polars code                                                      |
| `backup`             | —    | Scheduled cloud backups — `pg_dump` + full Qdrant snapshot → `rclone` remote (off by default; no port)               |

Inside the Compose network, services address each other by container name and the port from `config.yaml` (e.g. `http://agent:8000`, `http://forecaster:8001`). The `app` resolves these via `app/core/api_client.py`, which also honours `*_BASE_URL` env vars as overrides.

### Configuration

`_container_data/config.yaml` is the **single source of truth** for ports, hostnames, LLM/embedding settings, forecaster toggles, etc. It is bind-mounted read-only into every service.

Important: `docker-compose.yaml` duplicates the ports and bind-mount paths declared in `config.yaml`. Changing a port or path in one file requires changing it in the other. The two files are not auto-synced.

Each service parses the slice of `config.yaml` it needs through a small Pydantic model in its own `config.py` (`load_config(path)` → typed object; access is attribute-based — `CONFIG.postgres.host`, not `CONFIG.get("postgres", {}).get("host")`). Secrets are likewise typed per service via `pydantic-settings` `BaseSettings` in a `settings.py`, and each service declares and receives **only the secrets it actually uses** (least privilege): `clustering` / `forecaster` / `python_sandbox` get none, `agent` gets the read-only LLM role but not the superuser password, `app` gets both Postgres roles + the Qdrant key but no `OPENAI_API_KEY`. `docker-compose.yaml` enforces this at the container boundary — the old blanket `env_file: ./_container_data/.env` is replaced by a per-service `environment:` block that injects only that service's variables via `${VAR}` interpolation. A gitignored root-level `.env` symlink → `_container_data/.env` lets `docker compose up` resolve those `${VAR}`s with the documented command unchanged (alternatively: `docker compose --env-file _container_data/.env up`). There is no shared config/secrets package — each service is its own container with its own `pyproject.toml`, so the tiny models are duplicated per service by design.

Other config files in `_container_data/`:

- `.env` — secrets (Postgres creds, Qdrant API key, `OPENAI_API_KEY`, `FRED_API_KEY` for state indicators). Never commit; gitignored. No longer blanket-mounted into every container — each service receives only the secrets it uses (see the per-service scoping note above), and a gitignored root `.env` symlink points here so Compose `${VAR}` interpolation resolves.
- `database_schema.yaml` — column-level documentation of Postgres tables; mounted into `agent` so the SQL worker can ground its queries.
- `_configs/world_bank_download_config.json` — list of WB indicators grouped by dashboard page. Append here to add indicators on next clean boot; or add at runtime via the AI analyst (it calls `downloader_extra`).
- `_configs/news_download_config.json` — news topics for the RAG corpus (Webhose GitHub dataset).
- `_configs/actually_relevant_download_config.json` — Actually Relevant curated-news ingestion (`base_url`, `page_size`, and the 5 macro `topics` mapping each `slug` → Qdrant `collection`). The downloader fetches **all** stories (keyless JSON API) and buckets each into its macro-topic collection (`actually_relevant_<macro>`) via the `/api/issues` child→parent taxonomy.
- `_configs/world_bank_articles_download_config.json` — World Bank documents (WDS) RAG ingestion tunables (`base_url`, `rows_per_query`, `lang`, `from_year`, optional `doc_types` filter, `chunk_size_tokens`, `chunk_overlap_tokens`) plus a `queries` list of `{query, collection}` (~30 macro topics). Per query it fetches the top-N docs, pulls each doc's WB-provided plain text (`txturl` — no docling), token-chunks it, and uploads one point per chunk to `world_bank_<slug>`.
- `_configs/yahoo_download_config.json` — Yahoo Finance tickers.
- `_configs/binance_download_config.json` — Binance crypto ingestion tunables (`base_url`, `quote_asset`, `top_n`, `kline_interval`, `max_parallel_symbols`, `exclude_base_assets`). No curated coin list — the top-N coins are chosen at runtime by 24h quote volume.
- `_configs/fred_download_config.json` — FRED US-state indicators grouped by dashboard section. Each item is `{name, id (friendly slug), series_id (a representative single-state series like "CAUR")}`; the downloader resolves each `series_id` to a GeoFRED series group and fetches the whole 50-state + DC annual panel in one call. Append here to add indicators on next clean boot; or add at runtime via the AI analyst.
- `_configs/eurostat_download_config.json` — Eurostat EU NUTS-2 regional indicators grouped by dashboard section. Each item is `{name, id (friendly slug), dataset (a Eurostat dataset code like "nama_10r_2gdp"), filters (dims pinned to one category, e.g. {"unit":"EUR_HAB"}), units}`; the downloader fetches the whole NUTS-2 region×year panel in one keyless call (`geoLevel=nuts2`). Append here to add indicators on next clean boot; or add at runtime via the AI analyst.
- `_configs/nuts_level2_2021.geojson` — bundled GISCO NUTS-2 (2021) boundaries (`NUTS_RG_60M_2021_4326_LEVL_2`). Single source of truth mounted read-only into **both** `downloader_general` (builds the `eurostat_regions` catalogue from its properties — `NAME_LATN` region name, `NAME_ENGL` country name, `CNTR_CODE`, `LEVL_CODE`) and `app` (draws the Eurostat choropleth). Boundaries © EuroGeographics.
- `themes.yaml` — colour palettes. `active:` key selects one; bundled themes are `dark`, `dark-blue`, `light-green`. Drives both the registered Plotly template (`"app"`) and Streamlit chrome. **Deploy-time only** — the runtime theme picker was removed in v0.6. Adding a custom theme means covering every semantic token used in code (`positive`, `negative`, `reference_line`, `map_coastline`, `sector_*`, `diverging_*`, `sequential_*`, `card_title_color`, `confidence_band_alpha`, `selected_marker`, `wordcloud_background`, `wordcloud_colormap`) — `get_color` raises `KeyError` on a missing token, no silent fallback.
- `app/.streamlit/config.toml` — Streamlit's own theme/server config. Mirror of `themes.yaml` for the chrome side; edit `server.address = "0.0.0.0"` to expose the local dev build on the LAN.
- `backup/rclone.conf` — the rclone remote definition for cloud backups (cloud credentials). **Gitignored**; a committed `backup/rclone.conf.example` shows the shape (generate the real one with `rclone config`). Bind-mounted read-only into the `backup` service at `_container_data/rclone.conf` and passed to rclone via `--config`. The remote *name* here must match `backup.rclone_remote` in `config.yaml`. The non-secret knobs (`enabled`, `interval_minutes`, `rclone_remote`, `rclone_path`, `retention_days`, …) live in `config.yaml`'s `backup:` block.

### `app` (Streamlit)

Entry point `app/app.py` registers the Plotly template, sets up `st.session_state` (chat history, per-service health flags), declares the multi-page navigation, and shows a one-time data disclaimer dialog. Pages live under `app/pages/`, numbered `01_…` through `20_…` for ordering (the numbering also encodes the v0.3 navigation renormalisation). The indicator pages (`01`–`10`) are **config-driven** — they call `render_page_from_config` (`app/pages/page_utils.py`) with section keys from `world_bank_download_config.json` rather than hand-rolling charts; `14_yahoo_finance.py`, `15_news.py` and `16_crypto.py` are the bespoke "Other data" pages; `19_fred_regional.py` and `20_eurostat_regional.py` are the two bespoke pages under the **"Regional Statistics"** nav group. `19_fred_regional.py` is a catalogue-driven US-state view with a choropleth (`build_us_state_choropleth`), top/bottom state rankings (`build_region_ranking_bar`), and multi-state trends (`build_region_trend_lines`), all reading the `fred` tables via `get_fred_*` helpers; `20_eurostat_regional.py` is its EU analogue — a catalogue-driven NUTS-2 view reading the `eurostat` tables via `get_eurostat_*` helpers, reusing the same region-agnostic `build_region_ranking_bar` / `build_region_trend_lines` and a new `build_nuts_choropleth` (Plotly has no built-in NUTS geometry, so it draws the bundled GISCO GeoJSON via `geojson=` + `featureidkey="properties.NUTS_ID"`, loaded once by `core.assets.load_nuts_geojson`, and clamps the view to continental Europe); `17_token_usage.py` and `18_monitoring.py` are the two ops pages. `16_crypto.py` mirrors the Yahoo page (market overview table, top-coin log-scale trend, BTC candlestick, all-coin return-correlation heatmap) and reads the `binance_*` tables via `get_all_binance_historical_prices` / `get_all_binance_metadata`; its candlestick + heatmap come from the **generic** `build_candlestick_plot` / `build_correlation_heatmap` in `core/plotting.py` (the Yahoo page keeps its own `build_yahoo_*` variants). Shared infrastructure is in `app/core/`:

- `api_client.py` — typed wrappers around every backend HTTP endpoint (forecaster, agent SSE stream, clustering, plot interpretation, downloader_extra). Always use these wrappers rather than `requests.post` directly — they handle the base-URL resolution and request logging.
- `postgres_client.py` / `qdrant_client.py` — connection helpers with retries (hardened in v0.5).
- `plotting.py` — Plotly helpers; pages call `get_color` / `get_colorway` rather than hard-coding hex values, so palette swaps work via `themes.yaml`.
- `theming.py` — registers the `"app"` Plotly template from the active theme.
- `token_usage.py` — in-memory aggregator shown on the **Token Usage page** (`17_token_usage.py`); cleared on session end. `token_usage_store.py` is the separate Postgres-backed persistence layer (writes via the superuser role).
- `monitoring.py` — service-health probing + container stats behind the **Monitoring page** (`18_monitoring.py`). It hits each service's `/health` (`/_stcore/health` for Streamlit, a TCP/SQL probe for bare Postgres) and reads per-container CPU/memory/network from the Docker Engine API over a **read-only `/var/run/docker.sock`** bind-mounted into `app`. That mount is required for the Monitoring page and is declared only in `docker-compose.yaml`, not `config.yaml`.
- `app_logging.py` — centralised page-render and HTTP-request logging.
- `page_helpers.py` / `pages/page_utils.py` — shared dashboard-page rendering helpers (config-driven indicator renderer + common indicator-slice cleaning) extracted from per-page duplication; new indicator pages should reuse these rather than re-implementing the slice/clean/plot flow.

### `agent` (LangGraph supervisor)

`agent/agent/graph.py` is the heart of the AI analyst. The flow is:

1. **`GuardrailAgent`** — heuristic-first screen. Three regexes (auto-allow for short greetings + in-scope keywords, auto-block for clear red flags) decide most messages without an LLM call; only ambiguous ones escalate to the structured-output LLM.
2. **`MacroSupervisorAgent`** — plans, picks the next worker, and decides FINISH. Branches off `last_worker_status` (a `Literal["SUCCESS","EMPTY","ERROR","NEEDS_DOWNLOAD","BLOCKED","UNKNOWN"]` returned by every worker) rather than regex-matching prose. Static preamble + macro context block stay constant across turns so the prefix is provider-cacheable.
3. **Workers** (one of `WORKER_NAMES` in `graph.py`) — every worker also receives the last ~3 chat turns so follow-ups disambiguate:
   - `sql_agent` — up-to-5-step exploration. Defaults to WDI (`db_id = 2`) and skips the database-lookup step for typical macro queries; carries 3 worked few-shot examples.
   - `plotly_agent` — generates Plotly code, runs it in `python_sandbox`, returns the figure as an artifact.
   - `table_agent` — Polars transformations on prior worker output.
   - `rag_agent` — Qdrant semantic search over the news corpus.
   - `web_search` — DuckDuckGo fallback.
   - `downloader_agent` — calls `downloader_extra` to ingest data on demand from one of five sources (WB indicator, Yahoo ticker, Binance pair, FRED state indicator, Eurostat NUTS-2 dataset). Triggered when `sql_agent` returns `last_worker_status = NEEDS_DOWNLOAD`. The worker extracts a `DownloadPlan` (`source` + the source's id) and POSTs the unified `/ingest` body. For WB the exact `indicator_id`/`db_id` come from `sql_agent`'s `database_indicators` lookup; **Yahoo/Binance/FRED/Eurostat have no master catalogue**, so the worker infers the ticker / full USDT pair symbol / representative single-state FRED series id / Eurostat dataset code + filters (Apple→`AAPL`, Solana→`SOLUSDT`, state unemployment→`CAUR`, EU regional GDP per capita→`nama_10r_2gdp` + `{"unit":"EUR_HAB"}`) from the user request and `downloader_extra` validates it against the live API.
   - `chat_agent` — conversational synthesis / general-knowledge answers.

The graph builds **two `ChatOpenAI` instances** (`MacroAgentGraph.__init__`): a strong model (`shared.openai_llm_model`) for the reasoning-heavy roles — `supervisor` (planning + the final answer), `sql_agent`, `plotly_agent`, `chat_agent` — and a fast model (`shared.openai_llm_model_fast`) for the cheap `GuardrailAgent` screen and the lightweight `table_agent` / `rag_agent` / `web_search` / `downloader_agent`. Both share the base URL + API key and differ only by model name; when `openai_llm_model_fast` is unset it falls back to the strong model (the previous single-model behaviour). Vision (`/plots/interpret`) stays on the strong model.

When the supervisor picks FINISH, it writes the **complete polished markdown answer** into `isolated_worker_task` and that draft is streamed to the user verbatim in ~24-char chunks (`MacroAgentGraph._stream_supervisor_draft`). There is no second synthesis LLM call — the supervisor's draft is the answer, with only a small line-level leak filter (`_sanitize_draft`) stripping any line that accidentally contains worker names / sandbox / traceback tokens.

Streaming protocol is SSE on `POST /chat/stream` with `step` / `token` / `final` / `error` events; the `final` event carries the answer plus an `artifacts` dict and a `usage` block. `POST /plots/interpret` is a separate vision endpoint that reads a base64 Plotly screenshot with two modes (`no_hallucinations` strict description vs. analyst interpretation).

Per-LLM-call token accounting is attached via `UsageTracker` (`agent/agent/usage.py`) on every LangChain LLM in the graph (guardrail when it escalates, supervisor, each worker) — it's a graph-level callback, so it aggregates across both the strong and fast models automatically and labels each call with the model that served it. Worker output schemas live in `agent/agent/schemas.py`; prompt text lives in `agent/agent/prompts.py` and follows a stable-prefix / dynamic-tail layout so provider-side automatic prefix caching can match across requests.

External backend calls (sandbox, downloader_extra) use one shared `httpx.AsyncClient` from `agent.tools._get_httpx_client()` (closed in the FastAPI shutdown hook); the rendered database-schema text is `functools.lru_cache`d so it isn't re-serialised on every SQL step.

### `forecaster`

`forecaster/main.py` exposes a single `POST /predict` endpoint backed by seven model wrappers under `forecaster/forecasters/`:

| model id         | wrapper                          | notes                                                            |
| ---------------- | -------------------------------- | ---------------------------------------------------------------- |
| `auto_arima`     | `AutoArimaForecaster` (pmdarima) | non-seasonal `pmdarima.auto_arima`; refits per request           |
| `arima`          | `ArimaForecaster` (statsmodels)  | manual `(p, d, q)` from `model_params`                           |
| `sarima`         | `SarimaForecaster` (SARIMAX)     | manual `(p, d, q)` + `(P, D, Q, s)`; relaxed stationarity checks |
| `prophet`        | `ProphetForecaster`              | Facebook Prophet; `interval_width = 1 - alpha`                   |
| `chronos`        | `ChronosForecaster`              | Amazon Chronos T5 sample-based; preloaded at startup             |
| `moving_average` | `MovingAverageForecaster`        | flat-mean baseline; residual sd × √horizon CI                    |
| `xgboost`        | `XgboostForecaster`              | lag + rolling features, recursive multi-step                     |

Per-model hyperparameters travel in a single `model_params: dict[str, Any]` field on `ForecastRequest`; each wrapper's `predict` signature pulls the keys it needs by name (`p`/`d`/`q`, `window`, `lags`, …) and `**kwargs` swallows the rest. Adding a new model means: new file under `forecaster/forecasters/`, lazy-import branch in `_get_forecaster`, the id added to the `ModelType` literal in `forecaster/schemas.py`, the GraphBox UI in `app/core/plotting.py` (model dropdown option + a branch in `_render_model_param_inputs`), and a smoke test in `forecaster/tests/test_arima_smoke.py`.

`ARIMA_AVAILABLE` / `PROPHET_AVAILABLE` / `CHRONOS_AVAILABLE` toggles in `config.yaml` gate the three heavy-dep families. `auto_arima` / `arima` / `sarima` all ride on `ARIMA_AVAILABLE`. `moving_average` and `xgboost` are always available.

### Data ingestion

`downloader_general/src/` is split into `core/` (orchestration, schema validation in `utils/schema.py`, plus the shared `qdrant_uploader.py` embed-and-upsert mixin), `extractors/` (one module per source: `world_bank`, `yahoo`, `binance`, `fred`, `github` for the Webhose news repo, `actually_relevant_download` for the Actually Relevant curated-news API, `world_bank_articles_download` for World Bank documents), and `utils/`. The **initial** ingest is one-shot, gated by the `_container_data/downloader_general/.download_completed` marker (gitignored); re-running it from scratch requires removing that marker and the persistent volumes (`postgres_data`, `qdrant_data`). The container itself no longer exits — after the initial ingest it runs the incremental update scheduler described below.

**Incremental update scheduler.** After the initial ingest, `main.py` hands off to `src/scheduler.py:run_scheduler` (a SIGTERM/SIGINT-aware interval loop modelled on the `backup` service). Each source in the `config.yaml` `scheduler.sources` block has its **own** `interval_minutes` + `enabled`; every tick calls that source's incremental `update()` (append-only — **never** the destructive full `run()`, which drops+recreates). Both `run()` and `update()` share the same downloader objects built once by `build_downloaders()`. The whole scheduler is gated by `scheduler.enabled` (on by default; `run_on_start: false` waits one interval before a source's first update since the initial ingest just ran). A per-source `try/except` means one failing source is logged and retried next interval, never killing the loop; each tick re-runs `_initialize_connections(...)` first (cheap probe that also self-heals stale clients/transient outages) and skips the tick if it fails. What "un-downloaded" means per source: **time-series** (`yahoo`/`binance`/`world_bank`/`fred`/`eurostat`) read each item's latest stored period via `src/utils/incremental.py:group_max` (`max(date)`/`max(year)`) and append only strictly-newer rows into the existing tables (prior-year *revisions* are intentionally not re-pulled); `fred`/`eurostat` recover each concept's source id / dataset+filters from its `*_indicators` catalogue via `read_rows`. **RAG** (`news`/`actually_relevant`/`world_bank_articles`) dedup against Qdrant and upsert only new points **without** `recreate_collection` — via `qdrant_uploader.existing_payload_values` (scroll the dedup-key field) + `ensure_collection` + the mixin's `upsert_collections`; dedup keys are `archive_name` (news, per-archive), `article.id` (Actually Relevant story id), and `article.doc_id` (WDS document id). An `update()` whose value table is missing/empty (source never ingested) safely falls back to a full `run()`; `group_max`/`read_rows` return `None` only for a genuinely missing table (via `inspect().has_table`) and let transient DB errors propagate so a blip never triggers a destructive full re-ingest.

**News-file cleanup.** The Webhose news pipeline (`github_download.py`) clones + unzips into `_container_data/news`; `cleanup_downloaded_files()` deletes everything under that dir at the end of **both** `run()` and `update()` (after the Qdrant upload succeeds) so the multi-GB clone never lingers. Dedup uses Qdrant as the source of truth, so no on-disk state needs to survive. The other two RAG sources fetch from APIs straight to Qdrant and write no files.

Ingestion progress is reported **through the logs, not `tqdm`** (terminal progress bars don't render in container logs). Long loops wrap their iterable in `log_progress(iterable, label=..., total=...)` (`src/utils/downloads.py`), which emits a throttled INFO line (≤ one per 5 s, plus a final 100% line); git clone progress goes through the log-emitting `CloneProgress` in the same module. `tqdm` is no longer a declared dependency anywhere — reuse `log_progress` for any new progress reporting rather than reintroducing it.

Network resilience is centralised in two retry wrappers that **every** source funnels through: the async `wb_client.call_with_retries` and its synchronous twin `downloads._call_with_retries`. Both use **exponential backoff with jitter** (`wb_client.compute_backoff_delay`, nominal delay doubles per attempt capped at `max_delay=60s`, plus up to 50% random jitter) rather than a fixed pause — the jitter decorrelates the parallel workers so their retries don't reconverge on the API in lockstep, which is what provokes the WB rate-limit `400`s and Yahoo `curl (28)` timeouts. The per-downloader budget is `download_max_retries = 5` / `download_retry_delay_seconds = 5` (base). WB pagination has an **extra inner layer**: `wb_client._fetch_list` retries a single failed page via `_get_with_page_retries` (5 attempts, base 2s) so one transient mid-pagination `400` no longer discards the pages already fetched — the outer `call_with_retries` remains a final backstop. When tuning stability, prefer bumping these shared knobs over adding ad-hoc `try/except` in a single extractor.

World Bank access goes through a hand-rolled **async `httpx` client** (`downloader_general/src/utils/wb_client.py`), which replaced the old `wbgapi` dependency — it pages the documented `https://api.worldbank.org/v2/...` REST endpoints directly (`/source`, `/country`, `/indicator`, `/country/all/indicator/{id}`, `/sources/{db}/series/{id}/metadata` with a `/indicator/{id}` fallback) and returns plain dicts shaped exactly as the schema cast expects. Its client uses a generous read timeout (`DEFAULT_TIMEOUT = httpx.Timeout(60.0, connect=15.0)`). Aggregate economies (`region.id == "NA"`) are dropped (old `skipAggs=True` parity) and null observations kept; the indicator phase runs concurrently under an `asyncio.Semaphore(max_parallel_indicators)`. `downloader_extra` ships its own trimmed copy of the same client (`downloader_extra/wb_client.py`, data-fetch only) — duplicated per service by design, like the other tiny per-service models.

For incremental additions during a live stack, the agent's `downloader_agent` worker calls `downloader_extra` (port 8003), which writes directly into the running Postgres without touching the marker. `downloader_extra` is **multi-source**: its single `POST /ingest` dispatches on a `source` field (`worldbank` / `yahoo` / `binance` / `fred` / `eurostat`) to per-source clients (`client_wb.py`, `client_yahoo.py` using `yfinance`, `client_binance.py` + a trimmed `binance_client.py` copy, `client_fred.py` + a trimmed `fred_client.py` copy, `client_eurostat.py` + a trimmed `eurostat_client.py` copy). Each path short-circuits when the item is already present (`status="already_downloaded"`), else delete-then-inserts the freshly fetched rows (metadata row first to satisfy the FK). World Bank has the `database_indicators` master catalogue so `sql_agent` finds the exact id before downloading; Yahoo/Binance/FRED/Eurostat have **no master table**, so the agent infers the ticker / full pair symbol / representative single-state FRED series id / Eurostat dataset code (+ filters) from world knowledge and `downloader_extra` validates it live (yfinance history for Yahoo, `/exchangeInfo?symbol=` for Binance, `geofred/series/group` for FRED) — an on-demand FRED item is stored under the upper-cased series id as its `indicator_id` slug with `category="On-demand (FRED)"`.

Binance crypto ingestion (`downloader_general/src/extractors/binance_download.py`) goes through its own async `httpx` client (`src/utils/binance_client.py`), hitting only the documented public spot endpoints (`/api/v3/exchangeInfo`, `/api/v3/ticker/24hr`, `/api/v3/klines`) — no API key. It selects the `top_n` USDT spot pairs by trailing-24h quote volume (dropping stablecoins via `exclude_base_assets` and leveraged UP/DOWN/BULL/BEAR tokens in code), writes the ranked master data to `binance_metadata`, then pages each pair's full daily candle history into `binance_historical_prices` (PK `[date, symbol]`, FK → `binance_metadata.symbol`) concurrently under an `asyncio.Semaphore(max_parallel_symbols)`. The "description" is synthesized from documented fields (the REST API exposes no prose coin descriptions). Like Yahoo/WB it's marker-gated and bootstraps **only** its own `binance` schema group, so bulk top-N re-ranking on an existing volume needs a clean boot. For adding a single coin to a live stack there is now an on-demand path via `downloader_extra` (`source=binance`). It reuses the shared retry helper `wb_client.call_with_retries`.

FRED US-state ingestion (`downloader_general/src/extractors/fred_download.py`) goes through its own async `httpx` client (`src/utils/fred_client.py`) hitting the documented **GeoFRED** endpoints (`geofred/series/group`, `geofred/regional/data`) with a `FRED_API_KEY`. For each configured indicator it resolves a representative single-state series (e.g. `CAUR`) to a *series group*, then fetches the **whole 50-state + DC annual panel in one `regional/data` call** (`frequency=a` aggregates monthly/quarterly/weekly series to annual). The critical gotcha (covered by a unit test): several groups use per-state `series_id`s that do **not** encode the abbreviation (`MEDDAYONMARCA` → FIPS `06` = California, not "ME"), so observations are mapped to states by their **FIPS `code`** via the static `FIPS_TO_STATE` reference (also the source of Census region/division), never by parsing the series id. It writes three tables (schema group `fred`, mirroring World Bank's countries/metadata/indicators): `states` (id = 2-letter USPS abbrev, name, fips, region, division), `state_indicators` (one description row per indicator concept — friendly `indicator_id` slug, name, category, series_group, units, frequency, seasonal_adjustment, coverage), and `state_indicator_values` (long annual panel `(state, year, value, indicator_id)`, FK → `states.id` enforced). Like the other sources it's marker-gated and bootstraps only its own `fred` schema group. The app reads it via `get_fred_states` / `get_fred_indicators_catalog` / `get_fred_indicator` in `app/core/postgres_client.py`; `downloader_extra` ships a trimmed data-fetch-only copy of `fred_client.py` for the on-demand path.

Eurostat EU-regional (NUTS-2) ingestion (`downloader_general/src/extractors/eurostat_download.py`) goes through its own **keyless** async `httpx` client (`src/utils/eurostat_client.py`) hitting the documented Eurostat dissemination API (`.../statistics/1.0/data/{dataset}`), which returns **JSON-stat 2.0**. For each configured indicator it fetches the whole NUTS-2 region×year panel in one call (`geoLevel=nuts2`, `time` omitted → all years); the config's `filters` pin every non-geo/non-time dimension (`unit`, `sex`, `age`, `nace_r2`, …) to one category so a single clean series comes back. `parse_jsonstat` flattens the flat JSON-stat `value` map by **row-major stride decoding**, keeping only cells whose pinned dimensions sit at index 0 (so an under-pinned dim collapses deterministically to its first category) and only geo codes of the target level. It writes three tables (schema group `eurostat`, mirroring World Bank / FRED): `eurostat_regions` (id = NUTS-2 code, name, country_code, country_name, nuts1_id, level — built from the bundled GISCO GeoJSON so the catalogue exactly matches the map polygons), `eurostat_indicators` (one description row per concept — friendly slug, name, category, dataset, filters JSON, units, frequency, coverage, source_label), and `eurostat_indicator_values` (long annual panel `(region, year, value, indicator_id)`, FK → `eurostat_regions.id` enforced). Values whose region code isn't in the NUTS-2021 catalogue (older-vintage codes some datasets still return) are dropped. Like the other sources it's marker-gated and bootstraps only its own `eurostat` schema group. The app reads it via `get_eurostat_regions` / `get_eurostat_indicators_catalog` / `get_eurostat_indicator` in `app/core/postgres_client.py`; `downloader_extra` ships a trimmed data-fetch-only copy of `eurostat_client.py` (+ `client_eurostat.py`) for the on-demand path (`source=eurostat`, keyed on the lower-cased dataset code, `category="On-demand (Eurostat)"`).

The RAG corpus has **three** news sources beyond the Webhose GitHub dataset, all one-shot/marker-gated and all writing to Qdrant through the shared `src/core/qdrant_uploader.py` `QdrantEmbeddingUploaderMixin` (same `openai/text-embedding-3-small`, 1536-dim cosine space; `recreate_collection` + batched embed + upsert; one point per document). Every point keeps the news payload shape — a nested `article` dict (`title`/`text`/`url`/`published`/`thread.site`) plus top-level `topic`/`sentiment`/`date` — so the app news page (`15_news.py`, fully collection-agnostic) and the agent RAG worker read the new collections **unchanged**. (1) **Actually Relevant** (`src/extractors/actually_relevant_download.py` + `src/utils/actually_relevant_client.py`): a keyless curated-news JSON API that serves **analysis, not full article bodies** — so each point embeds a composed document (`compose_story_text`: title + summary + relevanceSummary + relevanceReasons + antifactors + quote + marketingBlurb) with the external `sourceUrl` kept as a link-out. Stories are paged from `/api/stories` and bucketed into one collection per macro topic (`actually_relevant_<macro>`, 5 collections) by mapping each story's granular `issue.slug` up to its macro parent via the `/api/issues` taxonomy. (2) **World Bank documents** (`src/extractors/world_bank_articles_download.py` + `src/utils/wds_client.py`, distinct from the indicators `wb_client.py`): per configured query it fetches the top-N docs from the WDS search API and pulls each doc's WB-provided plain text (`txturl` — **no docling**, keeps the image light), then token-chunks it (overlapping windows via the shared `tiktoken` encoding) into one point per chunk, one collection per query-topic (`world_bank_<slug>`, ~30 collections). These per-topic collection names don't follow the `{topic}_{sentiment}` convention, so the agent RAG search (`agent/agent/tools.py:_sync_qdrant_search`) **always folds in** any `actually_relevant_*` / `world_bank_*` collection (see `ALWAYS_SEARCH_COLLECTION_PREFIXES`) regardless of the topic/sentiment filter, then ranks all hits by score.

### `backup` (cloud backups)

`backup/` is a small **long-running** service (flat layout like `downloader_extra`) that periodically backs up both databases to a cloud remote via `rclone`. It is **off by default** (`backup.enabled: false` in `config.yaml`) and gated only by that flag — `docker compose up` starts it either way; when disabled it logs and idles on a `threading.Event` (so `restart: unless-stopped` doesn't restart-loop a clean exit). There is **no OS cron** — `main.py` is a simple `interval_minutes` loop (optional `run_on_start`, SIGTERM-aware), matching the repo's Python-everywhere convention. Each run (`backup_runner.run_backup_once`) is wrapped so one failure is logged and retried next interval rather than killing the loop.

Per run it: (1) `pg_dump -Fc` the Postgres DB as the **superuser** role (`backup_postgres.py`, password via `PGPASSWORD`, custom compressed format → restorable with `pg_restore`); (2) takes a **full-storage** Qdrant snapshot over REST (`backup_qdrant.py`: `POST /snapshots?wait=true` → stream `GET /snapshots/{name}` to disk → `DELETE` it server-side so Qdrant's ephemeral `/qdrant/snapshots` layer stays clean); (3) `rclone copy`s the staging dir (`postgres/` + `qdrant/` subdirs) to `<rclone_remote>:<rclone_path>` and prunes the remote `--min-age <retention_days>d` (`rclone_runner.py` — pure argv builders + subprocess). Staging is wiped before and after each run so only the current run is uploaded. Postgres and Qdrant live in separate stores, so backups are **not** cross-store transactional — the two captures just run back-to-back (as close in time as possible).

Config split follows the repo rule (no secrets in `config.yaml`): the `backup:` block in `config.yaml` holds the non-secret knobs (`enabled`, `interval_minutes`, `run_on_start`, `rclone_remote`, `rclone_path`, `rclone_config_path`, `retention_days`, `staging_dir`) and reuses the existing top-level `postgres:`/`qdrant:` host/port blocks; cloud credentials live in the gitignored `_container_data/backup/rclone.conf` (mounted read-only, `--config`). The container reuses the existing `POSTGRES_*` + `QDRANT__SERVICE__API_KEY` env — **no new `.env` vars**. The image adds `postgresql-client-18` (PGDG apt, matched to the server major) + `rclone` (multi-stage `COPY --from=rclone/rclone`). Restore is a rare manual op: `restore.py` (`docker compose run --rm backup python restore.py --list|--postgres FILE|--qdrant FILE`) automates `pg_restore --clean --if-exists` and downloads + prints the Qdrant full-snapshot recovery steps (a live-instance full-snapshot restore needs a boot-time `--storage-snapshot`, so it can't be a single API call).

## Conventions worth knowing

- The codebase uses **Polars**, not Pandas. Don't introduce `pandas` in new code.
- Charts are always **Plotly** going through the `"app"` registered template; pull colours from `core/theming` helpers rather than hard-coding.
- Agent worker outputs are **Pydantic models** (`agent/agent/schemas.py`); structured-output LLM calls use `with_structured_output(...)`. Adding a worker means: schema in `schemas.py`, tool wrappers in `tools.py`, node + supervisor routing in `graph.py`, and the worker name in `WORKER_NAMES`.
- Every backend HTTP endpoint should have a typed wrapper in `app/core/api_client.py` — don't bypass it from pages.
- Two Postgres roles: the superuser `POSTGRES_USER` (created natively by the `postgres:18` image at first volume init) is used by `downloader_general` / `downloader_extra` for ingestion writes and by `app/core/token_usage_store.py` for `token_usage` inserts; the read-only `POSTGRES_LLM_USER` is used by the `agent` (SQL worker) AND by the `app` for all `connectorx` page reads. `db_bootstrap.ensure_llm_role` grants the read-only role `USAGE` on `public` plus `SELECT` on all existing and future tables (via `ALTER DEFAULT PRIVILEGES`) — don't grant it anything more.
- DB access: the `app` keeps `connectorx` for bulk Polars reads; the `agent`'s `sql_agent` worker keeps raw `text()` because the LLM generates dynamic SQL. Everywhere else uses SQLAlchemy ORM (`select`/`delete`/`Session`) on `Mapped` models — don't sprinkle new `text()` calls.
- Postgres database name resolution: every client (`app/core/postgres_client.py`, `agent/main.py`, `downloader_extra/main.py`, `downloader_general/main.py`) reads `os.getenv("POSTGRES_DB") or config["postgres"]["database"]`. `POSTGRES_DB` in `.env` is the source of truth; `config.yaml`'s `postgres.database` is the fallback when the env var is unset. The postgres image itself only honours `POSTGRES_DB` at first volume init — changing the value on a populated volume requires re-creating the DB or wiping the volume.
- News page embedding panels (`app/pages/15_news.py: _render_embedding_map` and `_render_distance_histogram`) run only when their `st.form_submit_button` is clicked and cache the result in `st.session_state` so picking a different article re-draws the highlight on the cached projection without re-clustering. The scatter highlights the selected article using the `selected_marker` theme token; add that token to any custom theme before shipping it.
